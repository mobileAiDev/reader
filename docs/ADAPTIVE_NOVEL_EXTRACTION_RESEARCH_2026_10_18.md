# 自适应小说抽取：技术依据与建议

核查日期：2026-10-18。本文是可行性研究和架构建议，没有实现、设备基准或站点覆盖率验证。

## 判断

建议把目标定义为“减少逐站手工维护的自适应抽取引擎”。优先探索 **原文确定性抽取 + 自动发现/修复规则 + 小模型识别节点**。端侧模型与引擎可以组合；不建议从“训练一个模型替代全部书源协议”起步。这是工程建议，尚待本项目样本实验支持。

“转码”可以作为产品名称，但技术工作至少包括页面获取、页面类型识别、正文/目录/链接定位、结果校验与规则更新；单纯转换格式不能覆盖这些任务。

## 本项目已有基础

现有规则执行器已经使用 Jsoup 解析 HTML，并接入 `JsonPathLite`；因此确定性 DOM/JSON 执行层可以作为探索起点。[LegadoRuleEvaluator.kt](../source-engine/src/main/kotlin/com/ldp/reader/sourceengine/legado/LegadoRuleEvaluator.kt)

当前内置书源 JSON 含 203 条配置，其中 97 条设置了 `ruleContent.nextContentUrl`。这是配置数量统计，不代表独立模板数量、有效训练样本量或成功覆盖率；也说明不能用“单页有正文”代替同章分页完整性验收。[内置书源配置](../app/src/main/assets/source-engine/book-sources.json)

项目也已有从 `bge-small-zh-v1.5-onnx` 资源加载量化 ONNX 模型的代码，并接到 `V8SourceChapterValidator`。验证器处理的是章节标题、内容和前后章节语义上下文；这属于章节质量/语义验证，不能等同于 HTML 节点识别能力，也不构成当前设备性能验收。[模型提供器](../app/src/main/java/com/ldp/reader/source/SourceEngineV8BgeModelProvider.kt)、[章节验证器](../source-engine/src/main/kotlin/com/ldp/reader/sourceengine/content/v8/V8SourceChapterValidator.kt)

## 已有技术能支持什么

| 路线 | 第一方资料支持的能力 | 对小说阅读器的边界与推论 |
| --- | --- | --- |
| 通用正文抽取 | Mozilla Readability 接收 DOM，输出标题、正文 HTML、纯文本及部分元数据；其快速可读性检测明确可能出现误判。[官方仓库](https://github.com/mozilla/readability) | 适合作为章节页正文定位的基线；其接口并不提供完整的搜索、书籍身份识别、目录导航协议。后半项是根据接口职责作出的判断。 |
| 结构感知模型 | MarkupLM 联合建模文本和 HTML/XML 结构，论文评估网页问答与信息抽取任务。[原论文](https://aclanthology.org/2022.acl-long.420/) | 说明“学习网页结构并抽取字段”有研究依据，不证明中文小说、长目录或移动端部署已经适用。 |
| 节点监督训练 | 官方 MarkupLM 处理器支持文本节点、对应 XPath，以及训练时的节点标签 `node_labels`。[官方实现文档](https://huggingface.co/docs/transformers/model_doc/markuplm) | 现有规则可用作标注工具：在保留的页面上执行，记录命中的节点、字段、链接与文本。仅有选择器 JSON 没有页面和正确结果，不能直接形成这类完整训练样本。这是基于输入要求的推论。 |
| 移动端推理 | ONNX Runtime 支持 Android/iOS 推理；模型要能装入设备存储和内存，官方要求测量包体、模型体积、延迟与功耗。[移动端开发流程](https://onnxruntime.ai/docs/tutorials/mobile/) | “可以在手机上运行”与“本项目模型在目标手机上足够快、够省电”是两件事。本文没有为模型大小、速度或准确率作数值承诺。 |
| 模型生成可复用规则 | Crawl4AI 官方提供用 LLM 生成 CSS/XPath 抽取 schema、随后复用 schema 做常规抽取的流程，并支持执行验证。[官方文档](https://docs.crawl4ai.com/extraction/no-llm-strategies/) | 支持“模型负责找规则，运行时执行规则”的架构思路。文档的 schema 验证不等于整本小说正文完整性或跨页面稳定性验收。 |

以上能力都不应被解释为自动解决登录、访问限制、请求签名、加密接口或任意站点操作。正文识别组件的前提是已经取得可供识别的页面或数据。

## 建议架构：让模型定位原文，不让模型重写正文

以下是拟议设计，不是已有实现：

1. **获取层**：明确记录 HTTP 响应、渲染后 DOM 或 JSON，以及来源 URL 和获取状态。页面没取得时直接暴露获取失败。
2. **识别层**：判断搜索结果、书籍详情、目录、章节等页面类型；分别定位书名、章节条目、正文块、下一页/下一章链接。正文、目录和导航应分别评估。
3. **执行层**：模型只返回节点 ID、字段标签、候选排序或受约束的选择器；正文由程序从命中的原始节点复制。选择器无需通过生成任意 JavaScript 来执行。
4. **验证层**：检查正文污染/遗漏、重复页、章节身份、目录顺序和分页循环；保留 URL、节点位置和原文证据。验证不通过时返回明确失败或待修复状态。模型自报的“置信度高”不能替代这些检查。
5. **学习层**：把在多个页面上验证通过的抽取方案保存为可版本化规则；新站点或改版触发候选规则生成，再经过独立样本验证。普通章节读取复用已验证规则。

“已有规则 JSON”最有价值的用途，可能先是构建数据集和回归集，而不是立即训练大模型：

`有效旧规则 + 对应 HTML/JSON/渲染 DOM + 执行命中位置 + 人工校验结果 → 抽取训练/验证样本`

旧规则的输出应视为弱标注，需要抽样校验；过期规则产生的错章、广告混入或漏段不能当真值。对于只有处理后文本的历史样本，还需要重新定位源节点或单独标记其证据局限。

## 更经济的推进顺序

以下顺序是建议，不是已经证实的投入产出结论：

1. 建一组覆盖不同站点、模板、页面类型的可回放样本，人工确认正文与导航答案。按站点/模板家族分割训练和测试，另外保留改版后的时间外样本，避免同一模板的近重复页面造成虚高效果。
2. 对比现有规则、通用正文算法、模型生成选择器三条路线。先只验证“章节正文 + 同章分页”，必须区分下一页与下一章，确认章节内容完整合并且不混入后续章节，再扩展章节导航、目录和搜索，分别记录结果。
3. 若主要收益来自自动修复规则，优先在开发侧或受控服务侧完成生成、验证与下发；阅读端继续执行确定性抽取。若节点识别确实改善未见模板，再训练/蒸馏专用小模型，并在目标 Android 设备测量。
4. 衡量人工维护量是否下降，同时衡量正文完整率、广告混入、错章、目录遗漏、分页循环，以及端侧延迟/内存/能耗。不能仅以“成功返回了字符串”作为验收。

更低成本的产品补充是“用户点选一次正文/目录，系统归纳规则并验证同站多个页面”。它能为新模板提供可靠提示和训练标签，但仍是需要实现与测试的方案。

## 推荐表达

可以做，而且现有 JSON 规则是一笔可用资产。第一阶段更值得做的是 **能发现、验证、记住并修复规则的抽取引擎**；模型适合帮助理解页面结构。最终要证明的是维护成本减少、原文不丢不改、错章可检测，而不是给引擎冠以“万能转码”就获得这些能力。
